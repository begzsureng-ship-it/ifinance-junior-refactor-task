# iFinance — Шинэ төгсөгчийн код сайжруулах (Refactoring) даалгавар

Энэ төсөлд **3 бие даасан дасгал** орсон бөгөөд дээд хэсгийн цэсээр хооронд нь
шилжиж болно (`Nav` компонент, `pages/index.tsx`, `securities-state-mess.tsx`,
`securities-fetch-bug.tsx` эдгээрийн бүгдэд харагдана):

| Дасгал | Хуудас | Сэдэв |
|---|---|---|
| 1 | `/` (`pages/index.tsx`) | Ерөнхий кодын чанар (давхардал, `any`, imperative loop) |
| 2 | `/securities-state-mess` | State-ийн замбараагүй хэрэглээ |
| 3 | `/securities-fetch-bug` | `useEffect`/fetch-ийн буруу хэрэглээ |

## Зорилго

Гурван хуудас **бүрэн ажилладаг** (алдаагүй, зорилгодоо нийцсэн), гэвч кодын
чанар, зохион байгуулалт муутай. Таны даалгавар бол функциональ байдлыг
өөрчлөхгүйгээр (өөрөөр хэлбэл хуудас өмнөх шигээ ажиллах ёстой) кодыг **цэвэрлэж,
дахин зохион байгуулах** явдал юм.

## Ажиллуулах

```bash
npm install
npm run dev
```

Дараа нь `http://localhost:3000` хаягаар нээж, дээд цэснээс 3 дасгалын хооронд
шилжинэ.

⚠️ **Дасгал 3-ыг (`/securities-fetch-bug`) нээхэд console дээр `[fetchSecurities]
Хүсэлт #N` гэсэн лог тасралтгүй нэмэгдэж болзошгүй — энэ бол зориудаар бүтээгдсэн
алдаа. Ажигласны дараа тухайн цонхыг хааж/dev server-ийг зогсоож болно.**

## Хугацаа

**30–40 минут** (нийт 3 дасгалд, эсвэл дасгал тус бүрд ойролцоогоор 10-15 мин).

## Дасгал 1 — `pages/index.tsx` (Гүйлгээний жагсаалт)

### Одоогийн кодод байгаа асуудлууд

1. **Давхардсан код** — мөнгөн дүнг форматлах логик (`toLocaleString`-тэй адилтгах
   `replace(/\B(?=(\d{3})+(?!\d))/g, ",")` хэсэг) 3 өөр газар давтагдсан.
2. **Төрөл (type) байхгүй** — `transactions: any[]`, `render: (value: any) => ...`
   зэрэг `any` ашигласан тул TypeScript-ийн давуу тал (autocomplete, type safety)
   алдагдсан.
3. **Императив холбоос (imperative loop)** — `for` мөчлөгөөр шүүлт хийж, орлого/зарлага
   нийлбэрийг тооцоолсон нь `.filter()`, `.reduce()` зэрэг цэвэр функциональ
   аргуудаар илүү товч, ойлгомжтой бичих боломжтой.
4. **Бүх зүйл нэг компонентэд** — өгөгдөл, шүүлтийн логик, тооцоолол, UI бүгд нэг
   `Home` компонент дотор байгаа тул дахин ашиглах, тест бичих аль аль нь хэцүү.
5. **Inline style** — `style={{ padding: 24 }}` гэх мэт scattered inline
   style-ууд компонент болгонд давтагдана.
6. **Magic string давхардал** — `"success"`, `"pending"`, `"failed"` төрлийн
   утгууд хэд хэдэн газар (mock дата, `<Select>` сонголт, `columns` render)
   гараар бичигдсэн тул алдаа гаргах эрсдэлтэй (typo хийвэл ямар ч compile-time
   алдаа өгөхгүй).
7. **Тоон утга шууд бичигдсэн (magic number)** — `pageSize: 5` гэх мэт.

### Юу хийх ёстой вэ (заавал биш, санал болгож буй чиглэл)

- Мөнгө форматлах логикийг нэг дахин ашиглагдах функц болгон (`formatMoney` эсвэл
  `Intl.NumberFormat` ашиглан) гаргаж, 3 газарт дахин бичихийн оронд нэг л удаа
  дуудна.
- `Transaction` гэсэн TypeScript `interface`/`type` тодорхойлж, `any`-г сольж,
  `status` талбарыг `'success' | 'pending' | 'failed'` union type болгоно.
- Шүүлтийн логикийг `.filter()` ашиглан цэвэрлэнэ (`useMemo`-той эсэхийг мэдэж
  байвал нэмж болно, гэхдээ заавал биш).
- Дор хаяж нэг дэд компонент ялгаж гаргана — жишээ нь `StatusTag` (`status`
  props авч зөв өнгө/бичиг харуулах) эсвэл `SummaryCards` (орлого/зарлагын
  Card-уудыг харуулах).
- Боломжтой бол `status`-ын утгуудыг нэг газар (constant object/enum) тодорхойлж,
  бусад бүх хэсэгт тэндээс лавлана.

## Дасгал 2 — `pages/securities-state-mess.tsx` (Үнэт цаасны мэдээлэл)

### Одоогийн кодод байгаа асуудлууд

1. `filteredSecurities` нь filter-ээс "гарган авах" (derived) боломжтой утга
   атал тусад нь state болгож, `useEffect`-ээр гараар синхрончилсон.
2. `totalMarketValue` нь `filteredSecurities`-ээс дахин нэг давхар state +
   effect-ээр тооцоологдож, гинжин (cascading) effect үүсгэсэн.
3. `selectedSecurity` нь эх жагсаалтаас ХУУЛБАРЛАСАН тусдаа state тул үнийг
   "симуляцаар" өөрчлөхөд жагсаалт дахь өгөгдөлтэй зөрнө (нэг эх сурвалж
   зарчим зөрчигдсөн).
4. Sort хийхдээ массивыг in-place (`.sort()`) mutate хийгээд ижил
   reference-ээр л `setState` рүү дамжуулж байна.
5. `sortByPriceAsc`, `sortByChangeAsc` гэсэн 2 тусдаа boolean state ашигласан
   тул хоёулаа зэрэг "буруу" утгатай (зөрчилтэй) төлөвт орох боломжтой.

### Юу хийх ёстой вэ

- Derived утгуудыг (`filteredSecurities`, `totalMarketValue`) render дотор
  шууд эсвэл `useMemo`-гоор тооцоолж, тусдаа `useState`+`useEffect`-ийг арилгах.
- `selectedSecurity`-г бүхэл object хуулбарлахын оронд зөвхөн `id`-г хадгалж,
  харуулах үед эх жагсаалтаас `find`-аар олох (single source of truth).
- Sort хийхдээ `[...filteredSecurities].sort(...)` гэх мэтээр шинэ массив
  үүсгэх, эсвэл нэг `sortConfig: { field, direction }` state ашиглах.

## Дасгал 3 — `pages/securities-fetch-bug.tsx` (Үнэт цаасны хайлт)

### Одоогийн кодод байгаа асуудлууд

1. `params` нь render бүрд ШИНЭ object болж үүсдэг тул, `useEffect`-ийн
   dependency болгож ашиглахад render бүрд дахин ажиллаж, `setState`-тэй
   хамт тасралтгүй мөчлөг (loop) үүсгэнэ.
2. Дээрхтэй ДАВХАЦСАН, "эхний ачааллаар мэдээлэл татъя" гэсэн тусдаа нэг
   `useEffect(..., [])` нэмж бичсэн — mount дээр нэмэлт хүсэлт үүсгэнэ.
3. Хайлтын input бичих БҮРД (debounce-гүйгээр) шууд fetch дуудна.

### Юу хийх ёстой вэ

- `useEffect`-ийн dependency-д object бус, зөвхөн анхдагч (primitive) утга
  (`query`) ашиглах, эсвэл `useMemo`-гоор `params`-ыг тогтворжуулах.
- Хоёр дахь давхцсан `useEffect`-ийг устгаж, өгөгдөл татах цэгийг нэг л
  газар болгох.
- Хайлтад debounce (жишээ нь `setTimeout` эсвэл `useDeferredValue`) нэмэх.

## Хүлээгдэж буй үр дүн (бүх 3 дасгалд нийтлэг)

- Хуудас бүр өмнөх адилаараа ажиллана — **функциональ байдал өөрчлөгдөхгүй**.
- Кодын давхардал, `any` ашиглалт багасна.
- Derived утгыг state-д хадгалж, effect-ээр синхрончлох хандлага арилна.
- Дор хаяж нэг логик хэсэг тусдаа компонент/функц болж гарна.
